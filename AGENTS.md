# Сайт Кубыша: что нужно знать перед работой

Ты сопровождаешь сайт приложения «Кубыш», это iOS-приложение для личных финансов. На сайте два домена:

| Домен | Папка | Что там |
|---|---|---|
| `kubysh.com` | `landing/` | лендинг, SEO-страницы, политика ПД, пользовательское соглашение |
| `www.kubysh.com` | — | перенаправление 301 на `https://kubysh.com` |
| `pay.kubysh.com` | `pay-site/` | личный кабинет, оплата подписки, оферта, документы для Т-Банка |

Репозиторий: `github.com/pokirill/site`. API (`api.kubysh.com`) живёт в другом репо, `pokirill/Finik-backend`, здесь его нет.

## Как устроен прод

- **Сервер:** `root@201.24.56.21` (Timeweb, СПб), код лежит в `/root/site`, ветка `main`.
- **Путь запроса:** системный nginx на хосте принимает HTTPS (сертификат certbot, `cert-name kubysh.com`) и отдаёт сайт в контейнер `kubysh-site` на `127.0.0.1:8082`. API идёт в другой контейнер, на `127.0.0.1:8080`.
- **Где заголовки:** CSP, кеш и прочие заголовки задаются в `nginx/default.conf` этого репо. Системный nginx их не задаёт, его конфиг для справки лежит в `deploy/host-nginx.conf`.
- **Файлы запекаются в образ.** Правка файла на сервере руками ничего не изменит, нужна пересборка.
- **Выкатка:** после мержа в `main` выполнить `ssh root@201.24.56.21 'cd /root/site && bash deploy/deploy.sh'`. Скрипт откажется работать при грязном рабочем дереве на сервере. Он пересобирает только контейнер сайта и проверяет, что основные страницы обоих доменов отвечают 200.
- **Нельзя трогать:** контейнеры `app`, `postgres` и `nginx` из `/root/backend`. Это прод API с деньгами и данными пользователей.
- **Перед пушем:** `python3 -m pytest -q`. CI дополнительно собирает образ и прогоняет смоук-тест.

## DNS и сертификат

- **DNS `kubysh.com` в Cloudflare.** Доступа у агентов нет, записи меняет только Кирилл. Все записи серые (DNS only).
- 🚨 **Не заводить AAAA-записи на `kubysh.com`, `www`, `pay`.** В сентябре 2026 на них оставался IPv6 старого хостинга. Let's Encrypt проверял домен через него и не выдавал сертификат, и с вечера до утра сайт и оплата открывались с ошибкой сертификата.
- **Новый поддомен** требует трёх шагов: A-запись у Кирилла, блок в системном nginx, `certbot --nginx --expand`.
- **HSTS на `pay` стоит на год.** Если сертификат протухнет, кабинет станет недоступен, откатиться на http не получится. Автопродление работает через `certbot.timer`.

## Как проверять

- **Не с Мака Кирилла.** Там трафик идёт через Cloudflare WARP, DNS и доступность искажены. Проверять с сервера или с телефона без VPN, например `curl --resolve pay.kubysh.com:443:127.0.0.1 https://pay.kubysh.com/account/`.
- Команду `curl --resolve ...:127.0.0.1` выполнять только внутри SSH-сессии на production-сервере. При локальном запуске `127.0.0.1` укажет на компьютер агента, и проверка будет недостоверной.
- **Не во встроенном браузере Claude.** Он блокирует скрипты и стили `pay.kubysh.com` (`ERR_BLOCKED_BY_CLIENT`), кабинет выглядит сломанным, хотя работает. Вход через Apple и оплату проверяет человек на iPhone.

## Кабинет и оплата: что легко сломать

Подробно всё описано в `pay-site/README.md`, читать перед любой правкой в `pay-site/`. Учти, что разделы про `.htaccess` и «Рег.ру» там устарели: заголовки теперь задаёт nginx.

- **CSP строгий.** В `script-src` никогда не добавлять `'unsafe-inline'`, инлайновых `<script>` нет ни одного, тест это проверяет. Новый внешний домен (скрипт, API, шрифт) надо сначала добавить в CSP в `nginx/default.conf`.
- **Кеш.** HTML кабинета отдаётся с `no-store`. JS и CSS подключаются с `?v=ДАТА`: поменял файл, подними версию в HTML, иначе у людей останется старый.
- **Цены** приходят только из `GET /v1/web/plans` в копейках, в вёрстке их нет.
- **Вход только через Apple.** Popup, nonce и `state` устроены как в README, упрощать нельзя. Настройки Apple Service ID менять нельзя: от них зависит, что человек увидит в приложении подписку, купленную на сайте.
- **54-ФЗ.** Без email или телефона человек не должен дойти до оплаты, это состояние `state-contact`.
- **Автопродление.** Рядом с кнопкой оплаты обязательно условия и галочка согласия, которая по умолчанию не отмечена.
- **Страница успеха** не верит редиректу, а опрашивает API. Подтверждение от банка приходит отдельно, с задержкой.
- **Аналитики и трекеров на `pay.kubysh.com` нет** и быть не должно.
- **Реквизиты** (ИНН, ОГРНИП, «ИП Попов») не публиковать на транзакционных страницах, тест это ловит.
- **Адреса страниц** `/account/`, `/pay/success/`, `/pay/fail/`, `/offer/`, `/privacy/`, `/recurrent/` зарегистрированы в Т-Банке. Не переименовывать.
- **Возврат в приложение** идёт по `kubyshka://`, ссылка в App Store `https://apps.apple.com/app/id6778792103`.
- **Юридические тексты** оферты и регулярных операций присылает Кирилл от юриста. Агент их не сочиняет.
- 🚨 **Политика ПД существует в двух копиях:** `landing/privacy/` (основная) и `pay-site/privacy/` (копия под noindex). Правишь одну, обнови вторую.
- **Новый домен для оплаты** требует правки CORS в бэкенде (`app/core/config.py`, `allowed_origins`), иначе браузер заблокирует запросы к API.
- **Вебхук Т-Банка** указывает на `api.kubysh.com`, к сайту он отношения не имеет.

## Лендинг и SEO

- **Яндекс Метрика** `44147844` стоит на лендинге. В SEO-страницах клики в App Store отправляются событием `seo_appstore_click`.
- **SEO-страницы** генерирует `scripts/generate_seo_cluster.py`, результат пишется в `landing/`. Руками сгенерированный HTML не править, иначе правку затрёт следующий прогон.
- **Проверки SEO:** у каждой страницы уникальный canonical, новая страница добавляется в `sitemap.xml`, тесты это проверяют.
- **`<meta name="build">`** на главной обновлять при выкатке лендинга, по нему видно, какая версия на проде.
- **`pay.kubysh.com` закрыт** от индексации в `robots.txt`.

## Тексты на сайте

Позиционирование: сначала спокойствие («сколько можно потратить сегодня до получки»), потом «Получка», финансовые цели идут последними, как долгосрочная мотивация. Сэкономленное не привязывать к целям, лучше предложить человеку порадовать себя. Без длинных тире, без канцелярита и без обещаний, которых приложение не выполняет.

## Границы полномочий агента

- По умолчанию агент готовит изменения, запускает проверки и создаёт PR.
- Мерж в `main` и выкладка на production выполняются только по отдельному явному запросу пользователя.
- Наличие команды деплоя в этом файле не является разрешением выполнять её.
- Во время аудита, работы над текстами или подготовки PR не подключаться к production-серверу.
- Не изменять `pay-site/`, если задача явно не относится к кабинету, оплате или юридическим страницам.
- Не изменять DNS, сертификаты, системный nginx и инфраструктуру без отдельного запроса.
- Не добавлять в репозиторий токены, ключи, пароли, `.env` и другие секреты.

## Источники правды

- Актуальное описание продукта, функций и позиционирования: `github.com/pokirill/kubysh-marketos`, ветка `main`.
- Код и фактическое поведение сайта: этот репозиторий.
- Цены и состояние подписки: API `/v1/web/plans`.
- Юридические тексты: только материалы, переданные Кириллом от юриста.
- При расхождении маркетингового описания с фактическим поведением приложения не придумывать формулировку, а сообщить о расхождении.

## Работа с SEO-страницами

- Перед изменением SEO-страницы определить файл-источник данных и шаблон, которые использует `scripts/generate_seo_cluster.py`.
- Изменять источник или генератор, затем заново генерировать HTML.
- После генерации проверить diff: генератор не должен неожиданно менять страницы вне задачи.
- Не создавать несколько страниц с одинаковым поисковым интентом.
- Даты `lastmod`, `dateModified`, canonical и sitemap должны соответствовать фактическому изменению страницы.

## Проверка лендинга

Перед PR проверить:

- `python3 -m pytest -q`;
- сборку тем же способом, что использует CI;
- отсутствие `404` у всех локальных изображений, шрифтов, favicon и OG-обложки;
- главную на мобильной и десктопной ширине;
- ссылки App Store и события Метрики;
- canonical, robots.txt, sitemap.xml и JSON-LD;
- что изменения лендинга не затронули `pay-site/`.

В PR кратко указать:

- что изменено;
- какие страницы затронуты;
- какие проверки выполнены;
- требуется ли после мержа отдельная production-выкладка.

## Git

- `git fetch` до первой строки кода.
- Никогда `git add -A` и никаких масок: только явный список своих файлов. После коммита сверить `git show --stat HEAD`.
- Изменения идут через PR в `main`, выкатка только после мержа.
- Старые места сайта не использовать и не возвращать: папки `landing/` и `pay-site/` в `Finik-backend`, репо `fullbyte8179/Kubysh-web`, хостинг Рег.ру.
